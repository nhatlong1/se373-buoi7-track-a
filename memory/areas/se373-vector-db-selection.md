- Vector DB decision: Qdrant (self-hosted, client-server) for the SE373 BizCare final project.
- Chosen over Weaviate (too heavy, 2-4 GB RSS), Milvus standalone (needs etcd + MinIO, does not fit 4 vCPU), Elasticsearch/OpenSearch (JVM + Lucene, 3-5 GB), Chroma (no BM25, not production-grade), pgvector (no BM25, ts_rank is not BM25, conflicts with client-server preference), LanceDB/txtai (embedded only).
- Fallback if the host is smaller than specified: pgvector. Lightweight alternative: Redis Stack (RediSearch + vector sets).
- Qdrant satisfies requirements via: payload text index (BM25) independent of the HNSW vector index; VectorQuery and MatchText as separate query paths; FusionQuery with RRF for combined retrieval.
- Isolation design: one collection per workspace, named ws_<workspace_id>, PLUS a mandatory workspace_id payload filter on every query. Two layers of defence. workspace_id derived from the authenticated session, never from a request body; agent cannot choose a different workspace.
- Qdrant holds ONLY the latest indexed version of each document. Superseded chunks are DELETED from the collection, not merely flagged (decision changed 2026-10-23). The status=active filter remains as a second line of defence.
- Business-owner-set relevance score threshold applied at query time; chunks below it must not be used to answer.
- Memory budget on the 12 GB host: OS+Docker 0.5-1.0, FastAPI+embedding model 0.5-0.9, MySQL 1.5-2.5, SeaweedFS 0.3-0.6, Qdrant 0.5-1.5. Total 3.3-6.5 GB. Figures are estimates, not measurements.
- Qdrant memory levers: int8 scalar quantization, on_disk_payload, memmap_threshold_kb, max_search_threads=2.
- Per-workspace collection caveat: N collections cost more than one shared collection with N filters (min segment size per collection). Negligible at 2 workspaces. If workspace count grows, prefer shard_key_selector with workspace_id as shard key inside one collection.
- Embedding model: embeddinggemma2, text-only mode, Q4 quantisation, LiteRT-LM format (replaces the earlier multilingual-e5-small choice).
- INGESTION PIPELINE (7 stages, documented in output/ingestion-pipeline.md): (1) Validate - accept only txt, html, md, pdf, csv, xlsx; reject empty/duplicate; scan for prompt injection and viruses. (2) Normalise - Text type to MD (markitdown for HTML and PDF, txt not converted), Table type to CSV (one CSV per XLSX sheet); remove all image content; never alter Vietnamese characters. (3) Chunk - by section for structured files, by rows for CSV; txt by paragraph (proposal, unvalidated); every CSV chunk carries the header row. (4) Embed - embeddinggemma2 text-only, Q4, LiteRT-LM. (5) Index - staged write with indexed=false. (6) Mark as effective - old version superseded, new version effective. (7) Report status - pending/indexing/indexed/failed with reason.
- Chunk metadata = spec table plus an added `indexed` bool (staging flag). The spec `status` enum keeps exactly two values; `indexed` carries the staging state. Retrieval filter requires status=active AND indexed=true.
- RE-INDEXING (closed 2026-10-23, documented in output/reindexing-strategy.md): per-document re-index, NOT whole-workspace. Change detection via source_sha256 (file bytes) and content_sha256 (normalized text) compared at write time, not on a timer. Run order: normalize/chunk/embed FIRST, then delete old chunks, then write new chunks staged, verify count, flip indexed=true, then commit effective version in the document store, then audit log. Deliberate brief absence window (old deleted before new is live) - a missing answer is preferred over a stale policy answer. Retry: max 3, exponential from 5s. Job record in MySQL. index_config_version per document detects model/chunking changes.
